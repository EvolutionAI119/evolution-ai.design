# 第 6 章 契约优先的接口设计

> 作者：量子剑客
> 第二卷 · 架构：让复杂度各归其位

## 一、引言问题：为什么"跑通"不等于"可交付"

一个演示系统只需要一条能走通的路径；一个可交付系统必须回答另一组问题：谁可以调用、传什么、返回什么、失败时系统停在什么状态、下个季度新增的第十个模块会不会悄悄打破前九个模块的约定。当接口数量超过个位数，主要风险就从"功能有没有做"转向"约定有没有被守住"。

EVOLUTION AI 的接口面并不小：19 个路由模块、152 个路由端点，加上 `main.py` 直连的 2 个系统端点，共 154 个 HTTP 端点；17 张 ORM 表承载持久化状态。若每个模块各自约定字段名、各自解释状态、各自挑选错误码，154 个端点就会变成 154 套局部方言，前端每接入一个模块都要重新学习一次。契约优先要解决的，正是把"局部习惯"收敛为"全局可验证的约定"。

本章的核心命题是：**端点、数据表与状态机先于实现；字段 100% 对齐是硬约束。** 这里的"先"不是"文档先行、代码后补"的流程口号，而是指接口的形状必须在写业务逻辑之前就能被独立审阅、独立测试、独立回归。

## 二、原则

### 原则一 三层契约先于实现

一个端点的契约由三层组成：调用形状（方法、路径、鉴权等级）、数据形状（请求与响应的字段、类型、边界）、状态形状（合法状态与合法迁移）。三层确定之后，实现只是填充；三层未定之前，实现越熟练，返工越彻底。平台以 FastAPI 0.104 与 Pydantic v2 承载数据形状，全部请求与响应模型集中在 `backend/app/schemas.py`，运行时可从 `/docs` 读取 OpenAPI 描述；鉴权等级由依赖注入声明，而不是散落在函数体里的 `if`。

### 原则二 字段 100% 对齐，转换只允许发生在边界

后端使用 snake_case，前端使用 camelCase，这是两种语言的命名习惯，不是两套数据模型。平台只在边界做一次转换：`designer` store 的 `snakeToCamel` 统一处理来自后端的下划线字段，页面与组件此后只面对一种命名。训练样本的 `feature_order` 同样是一条硬契约：贝叶斯观测导出的特征顺序必须与训练管线逐位一致，否则"样本可训练"就只是一句愿望。

> **何时不适用**：公共 API 的演进期——外部消费者无法随仓库同步升级时，单点硬对齐让位于版本化契约（v1/v2 并存），字段冻结只约束同一版本内部。

### 原则三 状态机显式，错误码语义化

状态不能靠布尔标志的组合去猜测。工作流的合法状态是 pending、running、completed、failed，步骤级状态是 pending、completed、rejected，工作流级状态由步骤聚合推导，不存在手工置入的路径。错误也不能统一包装成 `200 + {success:false}`：400 表示业务校验失败，401 表示凭据缺失或失效，404 表示资源不存在，405 表示方法不允许，409 表示状态冲突，422 表示 schema 校验失败，503 表示可选能力未就绪。每种失败都有唯一出口，调用方才能写出确定的恢复逻辑。

### 原则四 契约必须可执行、可回归

写在文档里的契约会漂移，写在类型与测试里的契约才会报警。平台的约 1027 例自动化测试（算法 200、后端 411、前端 416，2026-10-25 实测，取自 VALIDATION_REPORT_20261025）中，后端套件直接覆盖路由契约、参数校验与错误分支，前端套件覆盖 API 模块与 store 的字段映射。契约不是评审会上达成的共识，而是每次提交都必须重新通过的门禁。

## 三、案例解剖：154 个端点如何保持同一种语言

先看鉴权契约。152 个路由端点按四档分布：公开 114、可选认证 9、必须认证 12、管理员 17。这不是一组随意的统计，而是"读基本公开、写收敛到认证、治理收敛到管理员"的结构性结果。游客模式让未登录请求以游客身份放行，管理端点仍要求管理员级依赖；同一套依赖注入既服务公开读取，也服务高权治理，不需要每个路由重复解释权限。

再看链路契约。登录认证到 Token 训练再到工作流审核的主链，横跨 auth、training、workflow、project 四个模块，共 41 个端点；这条主链真正调用的只有 6 个契约，占 14.6%。其余 35 个端点属于管理与扩展能力，不会被主链触发。这说明接口面的大小与链路的复杂度不必成正比：只要契约边界清晰，大接口面可以被小链路安全地消费。

贝叶斯模块展示了另一种契约密度。它只有 7 个端点，却把"会话生命周期"写得非常完整：创建时校验参数空间非空、参数名不重复、下界必须小于上界，否则 400；查询不存在的会话返回 404；尚无观测就查询最优返回 409，而不是返回一个伪造的空最优；上报观测时参数未知、缺失或越界一律 400。观测满两次之前建议走随机填充，满两次之后切换到高斯过程——状态与算法阶段被同一条契约表达出来，调用方无需猜测"现在到底能不能建议"。

品牌 DNA 则把契约做成了可交换的 schema。`BrandDNASchema` 固定版本号 1.0，要求顶层必须具备 `brand` 与 `on_brand_constraints`，判定状态只允许 PASS、FAIL、NO_DATA、N/A 四种，规则类型收敛为 zero、range、enum、sealed。更关键的是 NO_DATA 的语义：当前无法测量就如实标注，绝不推定通过。契约在这里不仅约束字段，也约束"诚实"本身。

**跨域映射。** 契约的诚实语义在语言模型系统里逐字成立：

- 在本平台 = 尚无观测就查询最优返回 409，品牌 DNA 无法测量时标注 NO_DATA 而非推定通过；在 RAG 系统 = 检索无依据时声明"不知道"，而非编造答案。空态必须有具名出口——契约不仅约束字段，也约束诚实。
- 在本平台 = 可选能力未就绪返回 503 并说明原因；在通用 Agent 系统 = 工具不可用时如实报告不可用，绝不返回伪造的成功结果。错误码语义化与"不伪装成功"是同一条契约纪律。

## 四、反模式与代价

**反模式一：接口即兴生长。** 先写页面，页面缺什么就临时加一个端点，字段名按当时方便命名。代价是端点数量增长快于理解速度，前端每接一个新模块都要读源码猜语义，最终 154 个端点变成 154 份口述传统。

**反模式二：字段双轨制。** 后端一套 snake_case，前端再造一套 camelCase，两边各自维护映射表。短期看不出问题，长期一定出现"某个字段只改了一边"的静默错误；这类错误不抛异常，只会让图表少一条数据。

**反模式三：状态藏在布尔组合里。** 用 `is_running`、`is_done`、`has_error` 三个布尔量表达状态，合法组合有八种，实际有意义的只有四种。代价是状态机无法被测试穷尽，审核驳回与任务取消经常落入未定义的中间态。

**反模式四：用 200 包装失败。** 所有响应都返回 200，再用 `success:false` 区分成败。代价是网关、监控与客户端重试策略全部失效：503 不再表示能力未就绪，409 不再表示状态冲突，排障只能靠读业务代码。

## 五、操作清单

1. 新增端点前，先在 `backend/app/routes/` 对应模块写清方法、路径、鉴权等级、请求字段、响应字段与全部失败码。
2. 为每个资源列出合法状态与合法迁移（参照 `workflow.py` 的步骤聚合方式），禁止用布尔组合隐式表达状态。
3. 统一命名转换点，只允许在 API 边界做一次 snake_case 与 camelCase 转换（参照 designer store 的 `snakeToCamel`）。
4. 为跨模块的数据顺序（如 `feature_order`）建立显式常量，并在消费端校验长度与顺序。
5. 用 `schemas.py` 的 Pydantic 模型约束边界值，不用函数体内的临时判断替代 schema。
6. 为每个错误码规定唯一触发条件，禁止"同一种失败返回多种状态码"。
7. 为契约写测试：成功路径、边界值、未知字段、缺失字段、越界值、状态冲突各至少一例（参照 `backend/tests/test_bayes.py` 与 `src/tests/api.spec.js`）。
8. 契约变更时同步更新 OpenAPI、前端 `src/api.js` 与测试，三者不得分批上线。

## 六、本章自检

1. 如果把实现代码全部删掉，只保留端点表、schema 与状态机，一个新人能否准确说出每个端点在什么条件下返回 400、404、409 或 503？
2. 你的前端是否只在边界做一次字段转换，还是每个页面都在自行猜测后端字段名？
3. 当某个可选能力缺失时，你的接口会返回 503 并说明原因，还是会返回一个看起来成功的假结果？
