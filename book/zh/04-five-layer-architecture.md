# 第 4 章 五层架构与薄壳编排

> 作者：量子剑客
> 第二卷 · 架构：让复杂度各归其位

## 一、引言问题：复杂度应该住在哪一层

一个常见的事故现场：前端拖动"车身长度"滑块，请求打到后端某个路由函数，函数里躺着三百行几何计算，计算中途要写数据库，失败时直接 return 一个 dict。半年后，这个函数谁也不敢动——几何专家不敢改，因为它连着鉴权；后端工程师不敢改，因为它连着事务；前端不敢改，因为响应形状是历史遗留。复杂度没有消失，只是住进了错误的楼层。

分层架构的老生常谈在 AI 原生系统里有一条新的理由：AI 组件的能力会持续演化，而 Web 系统的契约必须保持稳定。如果几何算法长在 HTTP 处理器里，那么每一次算法升级都是一次接口冒险；如果鉴权逻辑钻进算法包，那么每一次权限调整都要重跑数值测试。本章的核心命题是：**Web 层只做编排，算法内核可独立安装、独立测试、独立替换**。复杂度要各归其位，靠的不是约定俗成，而是依赖方向上的硬约束。

## 二、原则

**原则一：依赖单向，下层不感知上层。** 分层的价值不在分层图好看，而在依赖方向的单调：上层可以调用下层，下层不得 import 上层的任何符号。这条约束一旦成立，每一层都可以被单独理解、单独替换；一旦被破坏——哪怕只是一个"方便起见"的反向引用——分层就退化为文件夹命名。

**原则二：Web 层薄壳化，编排不计算。** HTTP 处理器的职责清单是固定的：参数校验、鉴权、持久化、编排、错误映射。它不含几何公式，不含优化数学，不含业务规则的手工实现。判断标准同样朴素：一个路由函数如果超过"接收—委派—返回"三段式，就是在偷偷长出第二颗心脏。

> **何时不适用**：需要复杂业务工作流引擎的系统——多分支、长事务、人工审批交织时，薄壳需让步于显式状态机，"接收—委派—返回"三段式不再够用。

**原则三：算法内核独立可安装。** 算法能力是系统的重资产，它应当有自己的包结构、自己的入口、自己的依赖清单与自己的测试套件。能否在一台没有数据库、没有 Web 框架的机器上 `pip install` 并跑通全部数值测试，是算法资产是否独立的试金石。

准确的边界是：L4 的核心内核为纯 numpy 实现，可 `pip` 独立安装、独立测试；深度学习与大模型不属于内核，而是可缺失的可选外挂——装上是增强，缺席是降级而非崩溃。层间分工的判据随之明确：编排（路由、鉴权、持久化、任务、密钥）在 L3，推理、提示策略、评分与训练在 L4 或可选能力层。证据是行为级的：PyTorch 缺失时，训练端点返回 503 诚实降级，而不是进程崩溃。

> **何时不适用**：大规模 GPU 训练场景——千卡级调度与吞吐优化超出纯 numpy 内核的射程，那一层应交给可选外挂层承接，内核原则不适用。

**原则四：能力边界画在层间。** 可选能力（PyTorch、CLIP、Redis、LLM）的探测与降级必须发生在层间接口上：下层如实报告"我缺什么"，上层据此决定降级路径并标注。层内不藏失败，层间不伪造成功。

## 三、案例解剖：五层如何各自就位

EVOLUTION AI 的五层划分是：L1 前端层（Vue 3.4 + Vite 5 + Three.js 0.166，12 个 Hash 路由页面）；L2 接入层（开发态 Vite Dev Proxy、生产态 Nginx，`/api/v1` 统一前缀，公网经 cpolar HTTPS 隧道）；L3 后端服务层（FastAPI 0.104 + Pydantic v2，19 个路由模块、154 个端点——152 路由 + `main.py` 直连的 2 个系统端点）；L4 算法层（`algorithm_model` 独立可安装包：car_modeling、freeform、surface_quality、storyboard 四个子包）；L5 基础设施层（SQLite + SQLAlchemy 2.0 共 17 张 ORM 表、文件存储、可选 Redis、Docker Compose 部署）。

> **两套视图，不要混读。** 「四层一通道」（图 4-2：意象—参数—曲面—工程）是**职责视图**，按产出物分工；本节 L1–L5 是**部署视图**，按运行时边界分工。二者不矛盾：职责视图中的"后端"在部署视图展开为 L2 接入层与 L3 后端服务层，"数据"展开为 L5 基础设施层；"前端"与"算法"两图同名同义。凡引用层数时，先说清是哪套视图。

薄壳的证据在端点里。以贝叶斯模块为例，`backend/app/routes/bayes.py` 的 7 个端点只做四件事：校验参数空间（非空、名不重复、下界小于上界）、委派 `bayes_optimizer.py` 的会话注册表、把优化器的显式异常映射为 HTTP 400/404/409、持久化观测。高斯过程的 Cholesky 分解、4096 点候选池打分、EI/UCB 计算全部在 L4 侧的纯 numpy/scipy 实现里，路由文件里没有一个数学公式。

算法独立的证据在测试里。L4 的 200 例 pytest 在无任何 Web 组件的环境下约 4 秒跑完；`algorithm_model/test_all.py` 提供一条命令的五模块自检（整车建模、曲面质量、模拟退火、分镜生成、全流程管线）。这两组测试不 import FastAPI、不连数据库、不起 HTTP 服务——L4 可以被单独克隆到任何一台机器上验证，这正是"独立可安装、独立测试、独立替换"的操作定义。几何内核升级时，154 个端点的对外语义保持不变；页面调整时，算法包不受牵连。

**跨域映射。** 分层与层间诚实不依赖几何内核：

- 在本平台 = 能力探测发生在层间，下层如实报告缺失、上层降级并标注（PyTorch 缺席时训练端点返回 503）；在通用 Agent 系统 = 工具不可用时编排层如实返回"不可用"，不伪装成功。层间接口是系统里最后一个可以说真话的地方。
- 在本平台 = 算法 200 / 后端 411 / 前端 416 三套测试按层独立可跑，替换某一层不惊动其他层；在 LLM 评测场景 = 单元评测、链路评测与端到端基线分层锁定，某一层漂移可单独报警。可验证性按层组织，是分层成立的硬证据。

## 四、反模式与代价

**厚控制器。** 路由函数里写业务逻辑，几何、事务、鉴权纠缠在一处。代价是改任何一件事都要理解全部三件事，回归测试无法定位失败，最终函数成为"谁也不敢动的遗产"。

**下层感知上层。** 算法包 import 了 Web 框架的异常类，数据层读取了请求上下文。看似省了一次参数传递，实则把整栋楼的重量压在了地基的某一个点上——此后 L4 的每次独立测试都要先搭起 L3 的脚手架。

**跨层直达。** 前端绕过编排直接调算法服务，或编排层绕过 ORM 直接拼 SQL。捷径每走一次，层间契约就磨损一分；等到需要替换某一层时，才发现契约早已名存实亡。

**层间伪造成功。** 下层依赖缺失，上层用假数据补齐响应。代价在第 1 章已述：信任只能透支一次。层间接口是系统里最后一个可以说真话的地方，这里失守，其他地方再诚实也无意义。

## 五、操作清单

| 检查项 | 通过标准 | 本仓库证据（文件或命令） |
|---|---|---|
| 依赖方向单调 | 全仓库无下层 import 上层的符号 | L4 `algorithm_model/` 零 FastAPI 依赖；分层约束见 `docs/ARCHITECTURE_DESIGN.md` |
| 路由薄壳化 | 处理器只做校验、鉴权、持久化、编排、错误映射 | `backend/app/routes/bayes.py` 等 19 个模块共 154 端点 |
| 算法包独立可安装 | 无 Web/数据库环境下安装并跑通数值测试 | `pytest algorithm_model/tests`（200 例，约 4 秒）；`python algorithm_model/test_all.py` |
| 层间有显式协议 | 每层对外协议单一（HTTP/JSON、函数调用、ORM） | L2 `/api/v1` 前缀；L3–L4 经 `algorithm_model/api.py`；L5 经 SQLAlchemy 2.0 |
| 能力探测在层间 | 可选能力缺失时下层报告、上层降级并标注 | PyTorch/CLIP/Redis 降级契约；后端 411 例测试含 503 分支 |
| 每层可独立验证 | 三层测试套件有独立命令与目录 | 算法 200 / 后端 411 / 前端 416，合计约 1027（2026-10-25 实测） |

## 六、本章自检

1. 你能否把算法目录复制到一台没有 Web 框架的机器上，并用一条命令跑通它的全部测试？
2. 你能否在不修改任何端点对外语义的前提下，整体替换某一层的实现？
3. 你的架构图里，是否存在一条从下往上指的依赖箭头？如果有，它为什么必须存在？
