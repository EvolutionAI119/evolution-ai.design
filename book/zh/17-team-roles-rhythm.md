# 第 17 章 AI 原生团队的角色与节奏

> 作者：量子剑客
> 第五卷 · 组织：人机如何分工
> 核心命题：六类角色、三种节奏、一条验收线。

---

## 一、引言：角色不是职位表，而是文档的责任结构

讨论 AI 原生团队时，最常见的问法是"还需要多少人、什么人"。这个问法本身就错了。AI 原生团队的组织设计不应从人头开始，而应从系统的承诺结构开始：平台对外做出的每一类承诺——设计哲学、开发方法、系统架构、接口契约、质量标准、验证证据——都必须有一个具名的守护者。承诺写在文档里，文档长在代码上，因此角色可以从文档体系反推出来。本仓库的知识底座恰好由六类文档构成：哲学、方法、架构、API、质量、验证。六类文档对应六类角色，这不是巧合，而是"文档即产品"在组织上的必然推论。

角色定了，节奏才有意义。AI 把执行速度提高了一个数量级，如果决策与验收的节奏不跟着重新设计，团队会被机器的速度拖垮：评审变成走过场，变更失去沉淀，快变量的噪声淹没序参量的方向。本章给出三种节奏与一条验收线，作为角色之外的时间维度。

## 二、原则

### 2.1 角色从承诺反推，不从技能正推

先列举系统对外做出的承诺类型，再为每类承诺设一个守护者。技能可以兼任，责任不能空缺。一个人可以戴两顶帽子，但每顶帽子在任何时刻只能有一个头。

### 2.2 六类角色各守一类文档

哲学守门人守设计哲学与元理论文档，裁决"这是否符合我们的设计观"；方法工程师守方法论文档，维护开发流水线与门禁规则；系统架构师守架构设计文档，冻结分层与边界；契约管理员守 API 参考，保证字段与端点 100% 对齐；质量工程师守质量标准与测试基线，定义判据、看护金字塔；验证负责人守验证报告与事实基线，对每一次发布签字。角色的权威来自其守护的文档，文档的效力来自角色的守护，两者互为凭证。

### 2.3 三种节奏分层运行，禁止串频

轮次级节奏（秒到小时）属于机器：贝叶斯单轮建议、测试红灯、构建反馈，由系统自动闭环，人只在异常时介入。迭代级节奏（周到双周）属于团队：方案评审、变体裁决、文档同步、缺陷复盘，按固定议程运行。演化级节奏（月到季度）属于总体：阈值调整、基线更新、知识体系修订、纲领自省，必须走知识层流程。用轮次级的速度改序参量，或用演化级的矜持拖住红灯处置，都是串频。

### 2.4 一条验收线，对所有人同一把尺

任何角色、任何节奏的产出，进入交付前都过同一条验收线：全部自动化测试通过、文档一致性审计零问题、关键决策留有证据链。验收线不因角色资历、截止日期或"这次改动很小"而弯曲。尺子只有一把，团队才有一致的质量语言。

## 三、案例解剖：六类角色在 EVOLUTION AI 的落点

把六类角色映射到平台，每一类都能指出具体的守护对象与验收物。哲学守门人守护设计哲学、设计元理论与系统思想三份文档，质量阈值 G1 5°、G2 2° 与 A/B/C/D 分界的任何调整必须经其裁决——因为阈值不是参数，而是设计观的编码。方法工程师守护开发方法论文档，五阶段流水线与阶段门禁的增删改是其职责范围。系统架构师守护架构设计文档，19 个路由模块、17 张 ORM 表、12 个页面的分层结构及其边界说明由其维护，任何新模块的落位需先过架构评审。契约管理员守护 API 参考，153 个端点（151 路由加 2 系统端点）的字段、错误码与状态机必须文档与实现 100% 对齐。质量工程师守护 955 例测试基线（算法 205、后端 388、前端 362），跳过与预期失败必须显式列示并附原因。验证负责人守护验证报告与事实基线，每次发布前实跑三层测试与一致性脚本，以真实输出签字。

三种节奏在平台同样有实证。轮次级：贝叶斯会话 20 至 40 轮进入 0.01 收敛带，机器自转，人只看异常与终态。迭代级：变体评审同时呈交质量报告、参数差异与回填记录，裁决留痕。演化级：测试基线从 201 例（2026-08-09）到 489 例（2026-09-27）再到 955 例的每次跃迁，都伴随文档、阈值与流程的同步修订——基线更新是演化级事件，不是日常变更。组织产出因此可以量化：19 模块、153 端点、955 例测试不是资产清单，而是六类角色在三种节奏上长期运行的沉淀物。

## 四、反模式与代价

| 反模式 | 具体表现 | 代价 |
|---|---|---|
| 角色虚设 | 文档有类别但无具名守护者 | 承诺无人背书，漂移无人发现 |
| 一人全角 | 所有角色集中于技术负责人 | 单点瓶颈，裁决排队，缺席即停摆 |
| 节奏串频 | 用单轮评分热度调整品牌阈值 | 序参量被噪声改写，系统失去方向 |
| 评审无证据 | 迭代级评审只看演示不看基线 | 决策不可回溯，同一争议反复 |
| AI 代签字 | 让模型输出直接充当验证结论 | 验收线失效，责任无法归属 |
| 双重验收 | 紧急需求绕过测试与审计 | 例外成为惯例，尺子失去公信力 |

## 五、操作清单

1. 六类承诺（哲学、方法、架构、API、质量、验证）是否各有具名守护者？
2. 每个角色的守护对象是否能指到具体文档与具体数字？
3. 轮次级事项是否有自动闭环，人只在异常时介入？
4. 迭代级评审是否有固定议程，且必须同时呈交证据链？
5. 演化级变更（阈值、基线、纲领）是否走知识层流程并留痕？
6. 验收线是否对所有角色、所有变更一视同仁？
7. 角色缺席时是否有明确的代理人，而非职责悬空？
8. 上一次基线更新，是否同步修订了相关文档与阈值说明？

## 六、本章自检

1. 把你们团队的文档按六类归档，是否存在"无人守护的类别"或"无文档支撑的角色"？
2. 最近一次阈值或基线变更，走的是轮次级捷径还是演化级流程？
3. 如果验收线对某次"紧急变更"弯曲过一次，它现在还是一条线吗？
