# 第 7 章 统一工作台：12 个页面的信息架构

> 作者：量子剑客
> 第二卷 · 架构：让复杂度各归其位

## 一、引言问题：页面越多，真相越少？

前端项目有一种常见死法：第一个页面精致，第五个页面开始各写各的，第十二个页面时，同一份项目数据在三个页面里有三个版本，同一台车在两个视图里长得不一样。页面数量的增长本身不是罪，真正的病是**每个页面都私藏一份状态、私藏一套逻辑、私藏一种对后端的理解**。病到后期，团队讨论的不再是"用户看到了什么"，而是"哪个页面说的是真的"。

EVOLUTION AI 有 12 个路由页面：Dashboard、Designer、DesignCopilot、Projects、ProjectDetail、DeepLearning、Quality、Deliver、Demo、Help、Community、Contact。它们共享 154 个后端端点——平均每页约 12.8 个。如果每个页面都自行组织数据与逻辑，12 个页面就是 12 个小型后端。本章的命题是：**页面不复述几何逻辑，状态只有一个真相源。** 统一工作台不是视觉风格统一，而是信息架构统一：页面只做呈现与交互，数据从唯一的 store、唯一的 API 层、唯一的后端契约流出。

## 二、原则

### 原则一 四段式编排，页面是最薄的一段

一次点击的完整旅程是：页面 → Store → API → 19 个路由模块 / 154 个端点 → 17 张表。页面组件不含几何逻辑、不含业务规则、不含字段猜测；它从 Pinia store 读取状态，调用 `src/api.js` 中按域导出的接口（`projectAPI` 到 `bayesAPI`），再把结果交给渲染。算法统一收敛到后端路由之后的 `algorithm_model` 层。页面要新增能力，第一反应应当是"这个能力属于哪个域的 API"，而不是"我在组件里算一下"。

### 原则二 状态只有一个真相源

全站共享四类 store：auth、designer、project、ui。任何数据只在一个 store 中持有权威版本，页面拿到的是引用而非副本。API 层同样唯一：`api.js` 维护一个 axios 实例（baseURL `/api/v1`），统一注入 JWT，统一处理 401——收到 401 时清除 Token 并广播 `evoai:auth-required` 事件，驱动全局登录态恢复，而不是每个页面各写一套跳转。

### 原则三 降级必须在界面上显形

统一工作台的统一，包括"失败的样子"也统一。后端不可用时，项目列表以 mock 数据兜底并标明来源；PyTorch、Ollama、CLIP、Redis 缺失时，对应能力区显示 503 或"仅几何特征"的降级标注，绝不伪装成功。游客模式下全站可读，触发写操作时弹出登录引导。能力有强弱，界面不含糊。

### 原则四 文案与语言也是架构

平台以 vue-i18n 承载中英双语，页面文案全覆盖。国际化不是上线前的翻译冲刺，而是信息架构的一部分：术语在两语言中指向同一个契约字段，知识库文档随平台语言切换。语言不一致的系统，本质上是两套系统共用一个域名。

## 三、案例解剖：12 个页面如何共用一套真相

<figure class="doc-figure"><img src="../docs/images/prod2-image.svg" alt="十二页面统一工作台插画：参数面板、三维视口与质量面板协同"><figcaption><strong>图 7-1 ｜ 一屏看懂统一工作台：参数面板 → 三维视口 → 质量面板</strong> 读图：左侧滑块是 22 维 CarParams 的可见切片，中间的整车侧廓由参数实时驱动并可拖拽旋转，右侧是同一模型的质量读数；底部十二个入口对应全部路由页面。关键结论是三类面板共享同一个模型状态——改一个参数，三维与质量同时变化，不存在三套数据。</figcaption></figure>

以 Designer 为例。它是平台核心工作台：车型、风格、品牌参数选择，`carAPI.generate` 生成整车并 3D 实时渲染，云端能力（数据集统计、合成样本批次、质量评估、生成式设计、参数优化）全部经 `aiAPI` 调用。页面里没有一行几何代码——它不知道曲面如何放样，只知道契约返回什么。

Deliver 页面展示了另一种统一：导入改参导出全链路（`importExportAPI`）被组织为一个会话对象——上传文件或 JSON 参数创建会话，查询参数树、修改参数、快照、3D 预览、多格式导出、下载，全部挂在同一个 session_id 之下。页面的信息结构直接镜像后端的会话契约，而不是另起一套前端私有模型。

DeepLearning 与 Quality 则共享"轮询同一真相"的模式：训练任务创建后，页面按秒轮询 `GET /ai/tasks/{id}` 直至终态；质量报告从 `qualityAPI.list` 读取，历史字符串报告自动规整为结构化展示。状态在后端，页面只是时间轴上的观察者。这也是约 1027 例测试中前端 416 例能够成立的原因：测试瞄准 store、API 模块与守卫，而不是逐像素瞄准页面。

**跨域映射。**

- 在本平台 = 12 个页面共用同一份 Pinia 状态与同一套 API 模块，任何页面都不私存副本；在通用 Agent 控制台 = 会话状态、工具调用与产物预览同源于一个运行态，切换视图不产生第二份真相。
- 在本平台 = 写操作先给乐观反馈、失败则回滚并显式报错；在 LLM 评测面板 = 评分提交后若后端拒绝，界面必须回退到未提交状态而非留一个假成功。

## 四、反模式与代价

**反模式一：页面私藏状态副本。** 每个页面把后端数据拷进本地变量各自加工。代价是同一份数据出现多个版本，"以哪个页面为准"成为长期争议。

**反模式二：组件内嵌业务逻辑。** 在 Vue 组件里写几何换算、写权限判断、写字段映射。代价是逻辑无法被后端契约约束，也无法被分层测试覆盖，改一处坏三处。

**反模式三：每页一套请求习惯。** 有的页面用 axios、有的用 fetch、有的直接拼 URL。代价是鉴权、错误处理与降级行为十二种写法，401 在某个页面静默消失。

**反模式四：降级无声。** 后端挂了，页面显示空表或永远加载中。代价是用户把"系统失败"误读为"没有数据"，决策建立在空白之上。

## 五、操作清单

1. 新页面立项时，先声明它消费哪些 store 与哪些 API 域，写进页面头部注释或文档。
2. 页面组件禁止出现几何计算与业务规则；发现即下沉到 store 或后端。
3. 所有请求经 `src/api.js` 的统一 axios 实例发出，禁止页面自建 HTTP 客户端。
4. 字段命名转换只在 store 边界发生一次，页面内不再出现后端原始命名。
5. 为每个页面定义降级态：后端不可用时显示什么、标注什么，写进组件并实现。
6. 页面文案全部走 i18n 键值，新增术语时中英同步入库。
7. 页面测试瞄准 store 与 API 模块（参照 `src/tests/` 现有 416 例），不测像素。
8. 涉及写操作的页面，统一接入 `evoai:auth-required` 登录引导，不自造弹窗逻辑。

## 六、本章自检

1. 任选一份业务数据，你能否在五秒内说出它的权威版本住在哪个 store、来自哪个端点？
2. 如果把某个页面整个删除，后端契约与其他页面是否完全不受影响？如果不是，说明逻辑放错了层。
3. 当后端整体宕机时，你的十二个页面各自会显示什么——是十二种意外，还是一种设计过的降级？
